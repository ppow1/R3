# R3A Unified Integration Inventory — cutoff 2026-11-08

## Release boundary

The integration branch is `integration/r3a-unified-20261109`. Its source cutoff starts at Coordinator commit `c02c882c4b8459a58df8ead4b8e41fd8f1065395`. ## Managed baseline at cutoff

At 2026-11-08 21:38 EST, the R3A PostgreSQL user service was active after crash recovery (PG 16.15, primary, database `r3a_ap0_m1`). Ring 0/CME had not started after reboot because of a user-unit ordering cycle. The provisioning template used `After=default.target` for PostgreSQL even though Ring 0 is wanted by `default.target` and waits for PostgreSQL. That concrete defect is corrected in this branch to `After=basic.target`; static systemd verification passed and Ring 0 was restored at 21:38:31 EST without changing database data.

At 21:39 EST, the user service was ACTIVE, Ring 0 PID 19681, CME PID 19702, restart count 0 since this boot. CME control diagnostics connect and report fresh process/database/module state under config digest `16ce490ef39cec48aa9d07f2d56321dc04f0276a243280f740ac7ebdd24d6c07`. The running interpreter is the Phase 0 virtualenv, but `WorkingDirectory` and code/artifact paths are the Coordinator worktree. The Coordinator parser accepts the running `module_manifest`; Phase 0 parser alone does not. This is now a traceable source boundary, not evidence that the Python environment itself is the release source.

Grace 1.2.11, Directory 1.1.1 and Telemetry 2.0.0 restored automatically. Knowledge 1.1.0 initially recorded FAILED/RuntimeError during startup, then its existing 1.1.0 provider was successfully activated via CME at 21:39 EST (PID 21311); the active version and grant were preserved. PostgreSQL showed 393,268 completed `foundation.observe` activities and exactly one queued observer at 21:39:38Z. This is a large durable completed history, not a 393k pending queue; the c02 observer correction is present and its current pending cardinality is one. The two legacy oversized Grace activities and all their evidence remain unchanged.
