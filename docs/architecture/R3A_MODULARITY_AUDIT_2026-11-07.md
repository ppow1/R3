## Core defects versus module behavior

1. **Genuine shared-core gap — lifecycle.** `CapabilityRegistry` supports register/discover/resolve, but `config.py` builds it at startup and `RegisteredOperation.load_provider()` imports Python code into the CME process. There is no runtime install/stop/replace operation, no versioned activation record, and no hot replacement; a provider upgrade requires restarting CME. This falls short of the already approved MOD-002–MOD-005 process/lifecycle contract. Implement one generic lifecycle/binding boundary once; do not add capability-specific loader branches.
2. **Capability behavior in core.** Notification intake and Engineering workflow/provider/verifier behavior are hard-coded in core paths. Knowledge retrieval has a plug-in package but retains operation-ID-specific grounding and a legacy core fallback. These should move behind reusable contracts rather than expanding core conditionals.
3. **Missing reusable contracts.** The operation contract covers a single authorized invocation; it does not declare a generic activity-input adapter or activity/workflow handler. Notification source ingestion and Grace's Engineering continuation therefore add per-capability CME/DB logic. Authentication has an identity assertion schema but no configured provider-binding contract.
4. **Integration conflict.** The modular-plug-in branch's deletions remove previously demonstrated Engineering capability files and tests. A successful merge would not make that work modular; it would lose it. Reconcile and preserve the existing contracts before integrating #46.

## Minimum corrections to document before implementation

1. **Generic activity-intake contract (`r3a.activity-intake.v1`).** Reuse `capability_operations` for source adapters. A versioned, typed result carries source/event identity, source idempotency key, parent activity/correlation, payload reference, evidence/provenance and a declared Grace task class. CME validates authorization, deduplicates, and persists through generic activity/event operations. Notification lifecycle records use the append-only generic event API; no `notification_sources`, `notification.ingest`, or notification-specific DB lifecycle methods in core. The adapter remains input/evidence only and cannot decide or acknowledge upstream work on receipt.
2. **Generic activity-handler contract (`r3a.activity-handler.v1`).** Let a registered module own domain workflow, versioned state and recovery policy, while CME provides generic scheduling, continuation/checkpoints, capability invocation/grants, and event persistence. First consumer is the existing Engineering workflow. Preserve the current Engineering operation, work-order, evidence, and verifier contracts as an adapter during migration; do not delete or duplicate them.
3. **Generic evidence enforcement.** Use each operation's declared evidence schema/verification obligations and canonical invocation result for knowledge grounding. Remove `institution.knowledge.read` conditionals only after the equivalent behavior is represented in the versioned contract and regression coverage; preserve legacy compatibility during migration.
4. **Configurable identity-provider binding.** Keep #49's session lifecycle and CME authorization in the shared service; load an implementation of `StewardIdentityProvider.verify(request) -> r3a.steward-identity.v1` through an external versioned manifest/config. Existing HMAC ingress is the first provider. #51 uses the same session and API contracts rather than a second bearer-token identity.
5. **Generic module lifecycle.** Use the approved module manifest (identity/version, contract range, dependencies, config/schema ref, artifact digest, state namespace/migration contract) for installed/active/stopped/failed/incompatible/replacing state. CME supervises activation, stop/drain, and version replacement without a Ring 0 restart; discovery remains separate from invocation authorization. This is shared infrastructure, not per-capability code.

## Continue integration

Keep PR #52 as an AP1 integration candidate for knowledge 1.0.1, observer queue correction, and notification evidence. Its current notification implementation is **not yet a plug-in delivery**. Document/agree contract 1 before moving notification-specific behavior out of core; document/agree contract 2 before moving Engineering workflow ownership. Continue AP1/website/auth work on isolated branches. Do not claim modular acceptance until installation/disable/replace without core-source edits and coexistence with existing capabilities are demonstrated against the declared lifecycle boundary.
