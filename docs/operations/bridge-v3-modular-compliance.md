# Bridge v3 modular compliance matrix

This matrix constrains Bridge v3 to the module and activity contracts already implemented in R3A. It does not create a second plug-in system, module lifecycle, registry, authorization plane, diagnostics service, or durable event log.

## Verified canonical contracts

| Concern | Verified source and contract | Current behavior |
|---|---|---|
| Versioned capability/module manifest | `r3a_runtime/capability_contracts.py::validate_module_manifest`; schemas `r3a_runtime/schemas/module-manifest.v1.schema.json`, `.v1.1.schema.json`, `.v1.2.schema.json` | The loader accepts `r3a.module-manifest.v1` versions 1.0.0, 1.1.0 and 1.2.0. v1.2.0 is the newest accepted schema. The provider runtime preserves the declared manifest version. |
| Configured discovery and artifact integrity | `r3a_runtime/config.py` capability operation loader; `r3a_runtime/capability_contracts.py::operation_from_manifest` | External manifests/config are schema-validated; artifact and supporting artifact SHA-256 values are checked; module identity, binding, operation refs and dependencies must agree. Unknown/invalid declarations fail closed before registration. |
| Provider interface | `r3a_runtime/protocol.py`; `r3a_runtime/provider_runtime.py::ProviderProcessManager`; `r3a_runtime/capability_contracts.py::CapabilityProvider` | CME starts one isolated provider process per module ID/version over the bounded private Unix-socket JSON-lines protocol. Health and lifecycle requests are correlated and versioned. The module does not connect directly to the institutional database. |
| Durable module lifecycle | `r3a_runtime/state_machines/module.v2.json`; `r3a_runtime/db.py::Store.register_module/module_state`; `r3a_runtime/provider_runtime.py` | CME owns `module.lifecycle` v2 transitions and the PostgreSQL `r3a.module_registry` projection. |---|---|---|---|

Keep countdown as local operator telemetry emitted by the transport host, not a fabricated CME heartbeat. | No bridge activity handler or Windows polling adapter is implemented. Must define a versioned request/progress/checkpoint/result contract and mock-test all-page batching. Windows poll proof remains live-only. |
| Windows v2 SendKeys transport | `r3a.capability-provider.v1` process interface; host-side adapter boundary | Preserve v2 unchanged. | Dispatch target routing | Versioned Bridge module operation/handler contract; CME activity input/checkpoint | Pure routing policy lives in the module; explicit target/session references arrive as contract data. | Session, queue, and delivery state | `activity.generic` and CME checkpoint/continuation/event lineage; module lifecycle is only for the Bridge module itself | Persist assignment work as CME activities/checkpoints and correlate GitHub IDs as safe evidence references. `QUEUE` waits through the durable activity queue. | Existing activity contract has no dedicated session registry or generic session-status API. ## Current implementation disposition

- **Verified manifest version:** the loader accepts module-manifest `1.0.0`, `1.1.0`, and `1.2.0`; use `r3a.module-manifest.v1@1.2.0` for new declarations because it is the newest accepted schema. Confirm its Activity Handler extension against `module_extensions.py` before declaring one.
- **Do not build:** a second SQLite module/session registry, a private lifecycle/state machine for module health, an independent auth/grant store, or a separate read/write diagnostics API.
- **Allowed next source increment:** add a Bridge capability as an external configured provider with a digest-pinned artifact, operation contract, module manifest v1.2.0 and mocked transport boundary. Route durable assignments through existing CME activities and lifecycle; no host adapter execution until scope/authority is explicit.
- **Unresolved architecture gap:** existing contracts do not yet provide a generic durable per-target session registry or a safe, authorized process/worktree/terminal provisioning operation. Those must be expressed as a versioned CME-mediated contract change or scoped as external adapter metadata before implementation; they cannot be smuggled in as a private bridge registry.
- **Acceptance:** source conformance and mocked provider behavior are distinct from Windows polling, multi-target delivery, restart deduplication, queue/steer, worktree provisioning and shared-runtime activation. None of the Windows/live claims is established by this matrix.
